## Decisions I was unsure about

- Routing: the task fits three decision-tree rows (filter, date, collect input). I read search-input.md first because it is the "filter" row, even though the bar has no text query. date-picker.md turned out to be the useful one: it has a filter-bar example that I followed closely.
- I read patterns/forms.md even though the "filter" row already matched. Its Structure section (single column, actions aligned to the end) is for forms, so I used only its labelling rules and kept the inline filter-bar layout from date-picker.md.
- Layout: date-picker.md's example uses a fixed `gridTemplateColumns: "2fr 1fr auto"` grid. I used a wrapping flex row with `flex: 2 1 auto` and `flex: 1 1 auto` so it stacks on narrow screens without any px/rem breakpoint. I can't run it, so the wrapping behaviour isn't verified.
- Gap between fields: `--spacing-md`, as in date-picker.md's filter bar, rather than forms.md's `--spacing-lg`, which is for vertical field stacks.
- "All statuses" uses the sentinel value `"all"`, because Select items can't have an empty value. An option with the value "all" would collide with it; I only noted that in a doc comment and don't guard against it.
- Reset goes back to empty filters (`EMPTY_FILTERS`), not to `defaultValue`. A caller that seeds the bar with preset filters might expect Reset to restore those instead.
- The Reset button is always enabled. I didn't disable it when nothing is set because a disabled button leaves the Tab order and focus would drop when it disables itself on click. A reviewer might prefer it disabled.
- No icon on Reset, so I didn't read foundations/iconography.md. date-picker.md's example uses a text-only outline button.
- The outer wrapper has `role="group" aria-label="Filters"`, and the date picker's own group wrapper sits inside it. The nested group is allowed but may be more than needed. I didn't use `role="toolbar"`, because that implies arrow-key navigation the controls don't provide.
- I added the "// eluan: composed, no component for …" comment. Eluan has no filter-bar component, but date-picker.md does document this exact composition, so the comment may not be needed.
- API: the component can be controlled (`value`/`onValueChange`) or uncontrolled (`defaultValue`), so the default export works with no props. That may go a little beyond what the task asked for.
- Labels are visible ("Date", "Status"), not aria-label only. forms.md allows aria-label only where a visible label would be redundant.
- Ids come from `React.useId()` so that several bars can sit on one page. These ids contain colons, which is fine for `htmlFor` and `aria-labelledby`.
- Typing: `next ?? ANY_DATE` on DateRangePicker's callback looks unnecessary to TypeScript, because the type says the range is never undefined. A strict `no-unnecessary-condition` lint rule might flag it, but date-picker.md says it is needed at runtime.
- Layout styles are an inline object with `satisfies Record<string, React.CSSProperties>`. That needs TS 4.9 or later, and I haven't confirmed the app's TS version.
