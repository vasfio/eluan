## Decisions I was unsure about

- Layout: I stacked the three sections on one page instead of using Tabs. Tabs would hide two-thirds of the settings, and the tabs settings example in the docs looked like a demo, not a recommendation.
- Section structure: each section's heading and description sit in a left column with the card on the right, wrapping to one column on narrow screens. I chose this over CardTitle because CardTitle is always an h3 (per the card docs), which would skip from the page h1 straight to h3. So headings are Typography with `as="h1"`/`"h2"`/`"h3"`.
- Wrapper styling: I used inline `style` objects with token CSS variables instead of `stylex.create`. The tokens page says tokens work in a `style` attribute, and the fieldset/switch docs snippets do this. I can't tell whether the app has the StyleX compiler set up. The catch: no media queries, so responsiveness relies on flex-wrap and flex-basis.
- Token names: I used `--spacing-*` (documented on the tokens page), not `--space-*` (used in the docs site's own StyleX but never documented).
- Label vs FormLabel: both appear in the docs. I used `Label` because the Label page documents its `required`/`optional`/`hint` props and its own example imports `Label`. I'm not sure they're the same component.
- `<Input label=...>`: one tabs snippet shows this, but the Input props table has no `label` prop and the matching demo uses a separate label. I treated the snippet as out of date.
- Refs: I assumed Input, EmailInput and Textarea forward refs to the native elements so I can move focus to the first invalid field. Getting Started says components use forwardRef, but EmailInput's ref type isn't documented.
- Using `validationTone` on EmailInput relies on "Forwards all Input props". Textarea doesn't document `validationTone`, so it only gets `aria-invalid` plus an error message.
- Error text color: `var(--destructive-fg)` on the normal page surface. I chose it because the theme-generator demo uses it that way and the xray config pairs `-bg-inverse` with `-fg-inverse` for solid fills. The success text uses `--positive-fg` by the same logic.
- No Toast: the docs say it needs `<Toast />` mounted at the root plus a direct `sonner` import. Neither is confirmed in this app, so feedback is inline: a live status line for success and a destructive Banner with `role="alert"` for errors.
- Notifications save on every toggle (optimistic, rolled back on failure), with no Save button. I went this way because the Switch docs call it a control "designed for immediate boolean settings".
- Switches stay enabled while a save is in flight, so keyboard focus isn't lost. A ref drops repeat toggles instead.
- Security alerts show an "Always on" Badge instead of a checked, disabled Switch. I did this mainly for UX (a control that can't be changed is confusing). Honest note: my auto-loaded memory index also mentions an Eluan contrast bug for checked+disabled controls. I didn't use that as a source, but it was in my context.
- No card entry on this page: I didn't use CreditCardInput. Raw card numbers should go through the payment provider's hosted flow, so the page only shows the saved card (brand, last 4, expiry) and calls `onUpdatePaymentMethod`.
- Data and handlers come in as required props (`profile`, `notifications`, `billing`, `onSave*`, and so on), since I don't know the app's API. The default export won't render without them. Initial values are copied into local state once, so to reset edits the parent remounts the page with a new `key`.
- Money is passed in minor units. The number of decimals comes from `Intl.NumberFormat(...).resolvedOptions().maximumFractionDigits`, with a fallback string for unknown currency codes.
- Dates: date-only ISO strings are read as local dates so they don't shift a day. There's an optional `locale` prop to avoid server/client mismatches when server-rendering. I added `"use client"` because the component uses hooks, assuming a framework that might be Next.js.
- `React.ComponentProps<typeof Badge>["variant"]` is used for the badge variant type instead of guessing an exported type name.
- Table cells can't be styled, so the Amount column is right-aligned with a block span inside the cell. The download column header is a visually hidden "Download".
- Invoices are sorted newest first in the component so the caption ("most recent first") is always true.
- Button has no documented loading prop, so the save and cancel buttons just change their label ("Saving…", "Canceling…") and are disabled. Disabling a focused button can drop focus in some browsers; I accepted that.
- Save and Discard are disabled until the form has changes.
- Wording that assumes things about the product (digest frequency, "paid features", the hint on the email field) is my placeholder copy.
- `role="list"` on the unstyled `<ul>` keeps list semantics in Safari.
