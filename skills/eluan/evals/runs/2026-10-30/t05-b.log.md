## Decisions I was unsure about

- Routing: the task matches two decision-tree rows ("Tell the user something happened" leads to feedback.md, and a signup form is "Collect input" which leads to forms.md). I read both, and they agree: an inline destructive Banner with role="alert" at the top of the form.
- There's no existing signup code, so I made up the contract: a `signUp(values)` prop that resolves `{ ok: false, message? }` when the server rejects and throws only on network or unexpected failures. A real app might throw on rejection instead, or return a string the way the forms.md example does.
- When the server sends a `message`, I show it verbatim, which assumes it's user-facing copy (stated in the JSDoc). Otherwise I fall back to "We couldn't create your account. Check your details and try again."
- I gave thrown errors different copy ("We couldn't reach the server…"), which assumes a throw means a network failure.
- Fields are email and password only, with no name field and no terms checkbox. That's a guess at the product's real signup fields.
- I added client-side field validation (required, email format, minimum password length) with FormMessage. That goes beyond the literal ask, but forms.md asks for field errors. The 8-character minimum is an assumed policy the server may not share.
- I wrote my own email regex instead of EmailInput `showValidation` / `onValidationChange`. The order in which `onChange` and `onValidationChange` fire isn't documented, so clearing the error while typing could have read stale validity. So there's no check/alert icon in the field.
- No `showStrengthIndicator` on PasswordInput, because I don't know the real password policy and the checklist must match the policy you enforce.
- Blur validation runs only when the field has a value, so tabbing through doesn't nag. forms.md just says "validate on submit and on blur".
- Every submit attempt clears the banner first. This keeps a stale server error from showing next to new field errors, and it re-inserts the alert so a repeated rejection is announced again. The trade-off is that the banner disappears while the request is in flight.
- Focus after a server rejection: Banner never moves focus, and I rely on role="alert" to announce it. Disabling the focused submit button during the request (as button.md and spinner.md prescribe) may drop focus to the body in some browsers, and I didn't restore it.
- I added a leading CircleAlert icon to the Banner (optional per banner.md; it keeps the error from relying on colour alone). It's sized with --size-xxs via an inline style on the Lucide element, which is my element, not an Eluan component.
- Submit sits in an end-aligned actions row, following forms.md, rather than the full-width button many signup screens use. The form has no max width; I left that to the parent, since there's no width token.
- Field messages have no trailing period, matching the component docs' examples ("Enter an email like name@company.com"). Banner copy does end with periods, per banner.md.
- The password error is "This password is too short" instead of repeating "Use at least 8 characters". The hint already states the rule and both are in aria-describedby, so repeating it would read the same sentence twice.
- I used `useId` for the ids so two forms on one page don't collide, which assumes React 18 or later.
