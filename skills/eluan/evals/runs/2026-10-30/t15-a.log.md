## Decisions I was unsure about

- **Import name:** I imported `Label`, not `FormLabel`. `package-components.ts` lists the import name as `FormLabel`, but every page and showcase that compiles imports `Label`.
- **Date range type:** The docs conflict. `page.tsx` uses react-day-picker's `DateRange`, while `demo.tsx` uses an inline `{ from: Date | undefined; to: Date | undefined }`. I derived the type with `React.ComponentProps<typeof DateRangePicker>["value"]`, so I don't import react-day-picker, which may not be a direct dependency of the app.
- **Labelling the date picker:** DateRangePicker documents no `id` or aria props. I gave it a name by wrapping it in `role="group"` with `aria-labelledby` pointing at a `Label` with an `id`. That `Label` has no `htmlFor`, so it's a `<label>` with no control.
- **Status select labelling:** `SelectTrigger` gets an `id` matched by `Label htmlFor`. I didn't add the `aria-label` the landing showcase also sets, because there it doesn't match the visible label text. I assumed `SelectTrigger` passes `id` and `ref` through to a `<button>`. The Getting Started page says every component uses `forwardRef`, and the showcase passes `id`.
- **"All statuses" value:** I used the sentinel `"all"` because Radix Select won't accept `""` as an item value. That rule comes from my own Radix knowledge; the docs only say Select is built on Radix.
- **Status options:** The task named no statuses. I picked defaults (Active, Pending, Completed, Archived) and made them overridable through a `statusOptions` prop.
- **State API:** I chose controlled-or-uncontrolled (`value` / `defaultValue` / `onValueChange`) over internal state only, guessing the page that fetches data will want to own the filters.
- **Reset target:** Reset returns to `defaultValue`, falling back to empty filters. It could instead always clear everything.
- **Reset when clean:** I disable Reset when there's nothing to reset. To avoid dropping keyboard focus to `<body>`, the reset handler moves focus to the status trigger first. Keeping Reset always enabled would also have been reasonable.
- **Reset styling:** I used `variant="ghost"` (the tokens page calls it tertiary/passive) rather than `outline`. The icon goes in as a child (`RotateCcw size={16} aria-hidden`), copying landing-showcase's `<Button size="sm"><Send size={14} aria-hidden />Send</Button>`. I assumed Button handles the gap between icon and text itself.
- **Spacing tokens:** I used `--spacing-*`. The docs site's own styles use `--space-*`, but globals.css shows those are local to the docs site, and the tokens page documents `--spacing-*` for consumers.
- **Label-to-control gap:** I picked `--spacing-xs` (from the Fieldset code sample and the collapsible demo). The rendered docs styles use 0.5rem (`--spacing-sm`), and the form-label demo uses 0.375rem.
- **Field widths:** The date field flexes from a 16rem basis up to a 22rem cap; the status field has a 12rem basis and a 10rem minimum. These assume Eluan triggers fill their container, which I inferred from landing-showcase's slot comments and the 24rem wrapper in the date-picker demo. They aren't measured.
- **Trigger text:** `dateFormat="PP"` (for example "Oct 30, 2026") keeps the range trigger short; the default is `"PPP"`. `placeholder="Any date"` shows that dates aren't being filtered. Both are judgment calls.
- **"use client":** The demos include it, so I did too. I don't know if the app is a Next.js app; elsewhere the directive is ignored (some bundlers may print a warning).
- **Partial ranges:** I assumed DateRangePicker may emit a partial range (`to` undefined) mid-selection and pass it straight through. Consumers have to handle it; this is noted in the type's JSDoc.
- **Outer group:** The whole bar uses `role="group"` with `aria-label="Filters"` (overridable), rather than `role="search"` or a `<form>`. Eluan controls aren't native inputs, so a native form reset wouldn't clear them anyway.
- **Not type-checked:** I couldn't run tsc or a build, so nothing has been compiled against the real `@eluan/core` types.
