## Decisions I was unsure about
- Banner vs. Toast vs. a hand-rolled error paragraph. I picked `Banner variant="destructive"`, rendered inline. Its docs page calls it a "system-level" strip (billing, downtime). package-components.ts calls it "a prominent inline message", and it's the only inline message component. Toast was ruled out because a form error should persist.
- Whether Banner already sets an ARIA role. The docs don't say, so I pass `role="alert"` (docs: it "Extends all HTMLDivElement props"). If Banner sets its own role internally, mine might be overridden or duplicated.
- Announcement strategy. I used role="alert" on mount and left focus on the submit button, instead of moving focus to the banner. To re-announce an identical repeat error, I clear the error before each submit.
- `Label` vs. `FormLabel`. package-components.ts lists the import name as `FormLabel`, but the form-label docs page imports and renders `Label` from "@eluan/core". I went with `Label`.
- Inline `style` objects vs. `stylex.create` for my own layout wrappers. I can't confirm the app has the StyleX compiler set up. The consumer-facing snippets (Fieldset usage, getting-started) use inline styles with tokens, and the tokens page says a style attribute works. So I used inline styles.
- Spacing tokens. I used `--spacing-lg` / `--spacing-xs` (documented on the tokens page; the Fieldset snippet uses `--spacing-xs` for label gaps). I avoided `--space-*`, which globals.css says is docs-only and doesn't exist in @eluan/core.
- The signup transport. No app code was available, so I invented `requestSignup` → `POST /api/signup` with a JSON body as the default `onSignup`. I assumed a `{ message }` or `{ error }` JSON error shape. The real call should be passed via the `onSignup` prop.
- What counts as "server rejects". 4xx: show the server's message, or a generic fallback. 5xx: generic copy, so server internals aren't leaked. Any other throw (network failure, or a bug): one generic "check your connection" message. These errors aren't logged anywhere, which could hide bugs.
- The form contents (email + password only, no name field), the copy text, and placing the banner at the top of the form rather than just above the submit button.
- `aria-disabled` + an in-flight ref guard instead of `disabled` on the submit button, to avoid losing focus. I don't know how Eluan's Button styles `aria-disabled`; it may look fully enabled while pending.
- Not clearing the error when the user edits a field. It stays until the next submit.
- No Spinner in the button. Spinner carries `role="status"` and `aria-label="Loading"`, which would leak into the button's accessible name.
- `CircleAlert` vs. `AlertCircle` from lucide-react. The installed lucide version is unknown. `CircleAlert` is the current name; very old lucide versions only have `AlertCircle`.
- I assumed React 18+ (`React.useId`) and that EmailInput / PasswordInput accept controlled `value`/`onChange` plus `id`, `name`, `required` and `autoComplete` (docs: they "Forward all Input props", and Input "Extends all standard HTMLInputElement props").
