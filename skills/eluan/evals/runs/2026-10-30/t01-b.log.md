## Decisions I was unsure about

- No link to the Terms of Service. SKILL.md says there's no Link component and points to Button `variant="link"` with `asChild`, but button.md says nothing about how that renders inline inside a Label or FormDescription (default size is `--size-lg` tall). checkbox.md's own sign-up example uses plain text, so I left the link out rather than guess. A real product would want one, probably passed in as an href prop.
- Blur validation runs only when the field has a value or already shows an error. Empty required fields are reported on submit. forms.md says "validate on submit and on blur", so this is a narrower reading, chosen so tabbing through the form doesn't show errors everywhere.
- While the user types, an error is only ever cleared once the value is fixed, never added or reworded. That's how I read "not on every keystroke. Keep the error until the value is fixed."
- Email validity comes from EmailInput's `onValidationChange`, not from my own regex, so the check/alert icon from `showValidation` can never disagree with the FormMessage. The catch is that the form depends on that callback firing on every change, as email-input.md says it does.
- Password policy: 8+ characters with an uppercase letter, a lowercase letter and a number, no special character required. The policy is mine; the task didn't give one. One `PASSWORD_POLICY` object feeds both `strengthRequirements` and my submit check, so they can't drift (password-input.md rules 4 and 5).
- There's no FormDescription stating the password policy before the user types. I relied on the strength checklist plus a FormMessage that spells out the rule on failure, to avoid saying the same thing twice next to the checklist. The downside is that screen-reader users only hear the policy after an error, because the checklist isn't linked via `aria-describedby`.
- For the terms checkbox I used the layout from checkbox.md (box on the left, label and error stacked in a column on the right, label line with `minHeight: var(--size-xxs)`), not the forms.md example (error under the whole row). But the column gap is `--spacing-sm` from forms.md, not the `--spacing-xxs` in checkbox.md's example, so the label-to-message gap matches the other fields.
- I wrapped the terms Label in a `div`, not the `span` in checkbox.md's example, because form-label.md says Label renders a block-level `<div>` row and a div inside a span is invalid HTML.
- Every field, the terms checkbox included, is marked with Label `required` and native `required` (one convention per form, forms.md rule 2; form-label.md rule 3). The form keeps `noValidate`, so native validation never blocks submit.
- The submit button is end-aligned (forms.md structure), not `fullWidth`, even though sign-up forms are often full-width.
- While submitting, the Button shows Spinner `size="sm"` (`aria-hidden`) and gets `disabled` and `aria-busy`, as spinner.md and button.md say. Disabling a focused button drops keyboard focus to the body, but that is what the docs prescribe. I did not disable the inputs.
- `onSubmit` returns `Promise<string | null | void>`: a returned string goes into the inline destructive Banner, and a rejection shows a generic Banner message. This follows forms.md's example signature, with the catch added. What happens after a successful sign-up (redirect and so on) is left to the parent.
- The form takes no width. It fills its container, and the parent page sets the width. I added no heading or other text, so I didn't read the typography files.
- After a failed submit, focus moves to the first invalid field (form-label.md accessibility). It's done in an effect after the re-render, so aria-invalid and aria-describedby are already set when focus lands.
- Ids come from `useId`, so two forms on one page don't collide.
- I couldn't compile or render anything, so prop types (for example `ref` on Input/EmailInput/PasswordInput/Checkbox, and `spellCheck` passing through EmailInput) were checked only against the API tables in the docs.
