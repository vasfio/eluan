## Decisions I was unsure about

- **`FormLabel` vs `Label`:** both appear as `@eluan/core` imports. `package-components.ts` names `FormLabel` as the import, and most demos use it, but the Label page's own example imports `Label`. I used `FormLabel`.
- **No required asterisks:** I didn't use FormLabel's `required` prop. Its props table sits on the page that demos `Label`, so I'm not sure `FormLabel` has it, and every field is required anyway. Each control gets `required` / aria-required instead.
- **Heading:** I used `<Typography variant="heading" as="h1">` instead of `CardTitle`. The docs say CardTitle renders an `h3` "by default" but don't document how to change it, and a signup page wants an `h1`. If the form is embedded in a page that already has an `h1`, this level is wrong.
- **Form wraps the whole Card:** I put `<form>` around the Card instead of inside it, so the submit button can live in `CardFooter` without adding a wrapper between Card and its sub-components. I don't know Card's internal layout.
- **Inline `style` on wrapper divs, not `stylex.create`:** the docs show consumer snippets with inline `style` plus tokens, and the README ships precompiled `styles.css`. The app may not have the StyleX compiler set up, so I didn't rely on it.
- **`--spacing-*` tokens, not `--space-*`:** `globals.css` says `--space-*` is a docs-site-only ladder that Eluan never defined, even though the docs' own StyleX uses it everywhere.
- **Muted text colour:** I used `--container-fg-alt` (through Typography `tone="muted"`), not the `--foregrounds-tertiary` that appears in the checkbox snippet. The tokens page says components should read the semantic layer, not the mode layer.
- **Error text styling:** errors use `--destructive-fg` on the container background, as in the theme-generator demo. They use the step-neg2 font-size, line-height and letter-spacing tokens, so they match the caption step. The docs examples use `--font-size-xs` instead, and Typography has no destructive tone.
- **`EmailInput` without `showValidation`:** I left its built-in check/alert icon off. Its regex isn't documented, and it could disagree with my validation message.
- **Password rules:** min length 8, plus uppercase, lowercase and a number. These are my choice, not a docs default. They're passed to `strengthRequirements` and reused for validation so the checklist and the enforced rule match. I'm assuming PasswordInput applies the requirements the way I re-implement them (ASCII `[A-Z]`, `[a-z]`, `[0-9]`).
- **Pass-through props:** I'm assuming `validationTone`, `aria-*`, `id`, `name`, `required` and `autoComplete` reach the real `<input>` on EmailInput and PasswordInput ("Forwards all Input props"). For Checkbox, I'm assuming `aria-invalid` and `aria-describedby` reach its button.
- **Focus by id:** I focus the first invalid field with `document.getElementById` in an effect, not with refs. The docs don't say which element each component's ref points to, but `id` + `htmlFor` clearly land on the focusable control.
- **Banner for form-level errors:** the docs describe Banner as a strip for system-level messages. I used it inline with `variant="destructive"` and `role="alert"`, and I'm assuming `role` passes through (it "extends HTMLDivElement props").
- **`CircleAlert` icon name:** I imported `CircleAlert` from lucide-react, the current name for the older `AlertCircle`. The docs only use `Info`, `Check`, `Copy`, `Plus`, `X` and `ArrowDown`, so the installed version is unverified.
- **Spinner in the submit button:** the Spinner has its own `role="status"` and `aria-label="Loading"`, which gets folded into the button's name. I'm also assuming Button spaces its children with a gap.
- **Terms links:** they open in a new tab with visually hidden "(opens in a new tab)" text, so the user doesn't lose the half-filled form. The `/terms` and `/privacy` defaults are placeholders.
- **`"use client"`:** included because the docs' examples are Next app router. It's harmless elsewhere, but the app's framework is unknown.
- **Component API:** `onSubmit` is required and may return `{ fieldErrors, formError }` for server-side errors such as "email already registered". Thrown errors show a generic message, and success handling (redirect etc.) is left to the caller.
- **When errors appear:** an empty field isn't flagged on blur, only after a submit attempt. The terms error appears only after a submit attempt. Once shown, errors update live as the user types.
